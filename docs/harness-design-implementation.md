# 디자인 게이트 구현 명세

> 2026-10-19 사용자 정정 후 실행 기준: [엄격한 레퍼런스 검증 1.1.0](harness-reference-fidelity.md). 아래의 대표 3장·승인 1회·G08/G09 미구현 설명은 당시 설계 이력이며 현재 실행에는 적용하지 않는다. 현재는 7유형·두 확인 지점과 rules.json 1.1.0을 따른다.

확정일: 2026-10-19
승인 근거: 사용자가 직전 라운드 세 질문에 “기본값”이라고 응답했다. 이 문서 저장과 아래 구현 범위를 확정한 응답이다. 실제 소단원의 대표 디자인 확인으로 사용하지 않는다.

기준 문서:
- [대표 디자인 검증 게이트](harness-design-gate.md)
- [디자인 검토 기록과 구현 규약](harness-design-review-contract.md)

## 1. 확정한 구현 범위

- G08은 대표 디자인 검증, G09는 사용자 대표 디자인 확인으로 분리한다.
- 자동 검사는 파일·해시·판정 누락·확인 대상 버전·미해결 의견의 일관성을 검사한다.
- 미감·수식 정확성·교육과정 적합성을 자동으로 보증하지 않는다.
- 하네스 구현과 격리된 삼투 현상 복사본 시험까지 진행한다. 실제 PPT·DOCX·Figma 디자인 재작업은 이번 구현에 포함하지 않는다.

현재 이 파일은 확정된 구현 명세다. 아직 rules.json, gate.py 또는 판정 상태를 변경하지 않았으며 구현·시험이 완료되었다고 보고하지 않는다.

## 2. G08 대표 디자인 검증

대상은 각 소단원 design-review/에 기록한 현재 대표 시안 버전이다. 계획 승인 이후 대표 장표를 제작하고, 전체 확장 전에 적용한다.

검사 조건은 다음과 같다.

- 그림 중심, 표와 수식, 비교 사진의 세 유형이 각각 한 개이며 유형 중복·누락이 없다.
- 각 대표 장표에 제목 계층·자료 크기·여백·이미지 배경·테두리의 다섯 항목 판정이 존재한다.
- 판정 상태는 기준 문서의 허용 상태에 속한다. failed와 unverified는 통과시키지 않는다.
- not_applicable에는 이유가 있다. 검사 대상 전체를 비워 자동 통과시키지 않는다.
- 원본과 시안의 식별 정보, 비교 화면, 판정 이유와 판정 주체가 있다.
- 참조한 파일과 화면이 실제로 존재하며 기록한 해시와 일치한다.
- 현재 계획·대표 시안·참고 원본·검토 버전의 연결이 일관적이다.

통과 의미는 비교 검토와 증빙이 완비되어 사용자에게 제시할 수 있다는 것이다. 스크립트가 외형을 직접 보고 미적 적합성을 증명했다는 뜻이 아니다. 실제 화면 검토 결과를 별도로 남긴다.

## 3. G09 사용자 대표 디자인 확인

G08을 통과한 현재 대표 시안 버전에 대해 적용한다.

- 해당 소단원과 현재 대표 장표 세 개의 버전에 연결된 명시적 사용자 확인이 있다.
- 계획 승인, 다른 시안의 확인, 무응답, 에이전트의 자체 판정을 대신 연결하지 않는다.
- 확인 후 대표 장표의 내용 또는 배치가 변경되어 현재 버전과 달라지면 기존 확인을 그대로 유효하다고 처리하지 않는다.
- open 또는 revised 상태의 거부·수정 의견이 남아 있으면 실패한다.
- 전체 스타일 거부를 국소 수정만으로 닫거나, 해결 근거 없이 resolved로 기록한 경우 실패한다.
- 사용자 확인의 근거 응답과 대상 버전의 연결을 검사하며 실제 사용자 확인 여부를 에이전트가 창작하지 않는다.

G09 통과 이후에만 나머지 장표로 확대한다. 새 유형이나 전체 외형 변경이 생기면 대표 디자인 검토로 복귀한다. 이후 전체 검수에서도 미해결 디자인 의견이 생기면 완료를 막는다.

## 4. 기존 파이프라인과의 연결

순서:

근거 분석 → 페이지 계획 → 계획 승인 → 이미지 준비 → 대표 3장 제작 → G08 → 사용자 대표 디자인 확인 → G09 → 전체 제작 → 전체 검수·Figma 대조 → 최종화

기존 G03의 계획 승인 전 이미지 생성·본 제작 금지와 G07의 원본 보호는 유지한다. 대표 3장 제작에는 전체 목표 장수를 요구하는 기존 G05를 그대로 적용하지 않는다. 대표 제작과 전체 제작의 선행 조건 및 쓰기 경계를 구분하여 구현한다.

전체 제작 진입과 최종화에서 G08·G09의 현재 유효성을 검사한다. 과거 단계 체크포인트가 남아 있다는 이유로 새 검사를 생략하지 않는다. 단계 입력이나 대표 시안이 변경되면 의존하는 확인과 후속 체크포인트를 다시 판단한다.

기존 작업을 읽거나 이력을 보존하는 기능과 새 조건에 따라 전체 확장·최종화하는 기능을 구분한다. 이전 최종본을 삭제하거나 과거 승인 기록을 새 승인의 형식으로 변환하지 않는다. 새 증빙이 없으면 새 게이트 미통과로 보고한다.

## 5. 자동 검사의 한계

자동 판정 범위:

| 검사 대상 | 기계가 확인할 내용 |
|---|---|
| 파일·화면 | 존재 여부, 해시 일치, 필수 연결의 누락 |
| 대표 시안 | 세 유형의 개수·중복·누락, 현재 버전 일치 |
| 항목별 판정 | 필수 항목·허용 상태·이유·증빙·판정 주체의 누락 |
| 사용자 확인 | 기록 존재, 소단원·대표 버전·근거 응답 연결 |
| 거부 의견 | 고유 번호, 상태, 영향 범위, 수정본·재확인 연결, 미해결 건수 |
| 재개·최종화 | 이전 확인의 현재 유효성, 후속 상태의 일관성 |

기록의 존재는 내용이 진실하다는 자동 증명이 아니다. 글자가 잘 읽히는지, 수식의 기호가 정확한지, 원본 스타일과 어울리는지는 실제 검토가 필요하다. 이 기능들을 구현하지 않고 자동 검사 결과로 보증했다고 설명하지 않는다.

추가 점수제, 미감 점수 임계값, 근거 없는 자동 이미지 품질 판정은 이번 범위에 넣지 않는다. 기계 조건의 단일 기준은 구현 후 rules.json으로 유지하고 문서에서 중복된 별도 수치를 운영하지 않는다.

## 6. 구현 대상과 보호 범위

구현 시 다음 파일을 정합화한다.

- harness/rules.json: G08·G09의 조건, 단계·재개·최종화 연결에 필요한 계약
- harness/gate.py: 새 판정, 단계 경계, 버전·확인·거부 의견 검사
- harness/validate.py 및 관련 시험 자료: 정상·실패 주입·재개·최종화 시험
- AGENTS.md 및 기존 하네스 문서: 사람 확인 두 곳, 대표 제작 단계, 실패 복귀와 구현 현황
- harness/README.md와 검증 보고서: 실제 명령·기록 계약·실행한 시험 결과

필드명·버전 계산·게이트 호출 위치 등은 위 확정 조건을 충족하도록 구현하되, 실제 계약을 사용법과 함께 공개한다. 조건을 완화하거나 사용자 승인을 추정하여 구현을 통과시키지 않는다.

보호 원본은 변경하지 않는다. 실제 삼투 현상 PPT·DOCX·Figma 및 실제 사용자 승인 기록은 구현 시험의 수정 대상이 아니다. 운영 규칙 변경에 따른 현재 실제 작업의 미통과 상태는 정직하게 표시한다.

## 7. 복사본 검증과 완료 보고

삼투 현상 폴더의 격리된 시험 복사본에서 검토 기록 규약의 필수 사례를 모두 실행한다. 정상 사례의 합성 확인은 시험 모드에서만 사용하며 실제 최종 결과물 발행은 금지한다.

검증 보고서는 사례별 입력 조건·기대 판정·실제 판정·증거를 포함한다. 실제 사용자 확인 부재, 오래된 확인, 비교 화면 누락·해시 불일치, 유형·항목 누락, 미해결 거부, 국소 수정으로 전체 거부를 닫으려는 시도, 변경 후 재개, 시험 승인으로 실제 발행 시도를 확인한다.

기존 필수 회귀 검사도 실행해 원본 보호와 기존 계획 승인·제작물 검사 등이 유지되는지 확인한다. 실패가 남으면 구현 완료로 보고하지 않는다. 실행하지 않은 시험은 미실행으로 구분한다.

완료 보고는 하네스 구현 결과, 복사본 검증 결과, 실제 소단원에 남은 디자인 확인을 분리한다. 구현·시험 통과를 실제 삼투 현상의 디자인 승인 또는 재제작 완료라고 표현하지 않는다.
