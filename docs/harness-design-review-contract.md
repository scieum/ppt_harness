# 디자인 검토 기록과 구현 규약

> 2026-10-19 사용자 정정 후 실행 기준: [엄격한 레퍼런스 검증 1.1.0](harness-reference-fidelity.md). 아래의 대표 3장·승인 1회·G08/G09 미구현 설명은 당시 설계 이력이며 현재 실행에는 적용하지 않는다. 현재는 7유형·두 확인 지점과 rules.json 1.1.0을 따른다.

확정일: 2026-10-19
승인 근거: 사용자가 직전 라운드의 세 질문에 “기본값으로 ㄱㄱ”라고 응답했다. 이 문서의 저장과 세 기본 정책을 확정한 응답이다. 개별 소단원의 디자인 승인이나 구현 완료 증빙으로 사용하지 않는다.

기준 설계: [대표 디자인 검증 게이트](harness-design-gate.md). 이번 라운드는 검토 기록의 위치, 거부 의견의 추적, 복사본 선행 시험을 확정한다.

## 1. 기록 위치와 버전

각 소단원의 design-review/에 원본·시안 비교 화면, 항목별 판정, 사용자 확인 기록을 모은다. 원본 자료는 읽기 전용으로 유지하고 비교용 파생 화면만 이 폴더에 저장한다.

권장 구조는 다음과 같다. 필드명과 실제 파일 이름의 기계 검사 계약은 구현 라운드에서 확정한다.

```text
units/단원번호_소단원명/
  design-review/
    versions/버전ID/
      references/         원본 비교 화면
      candidates/         대표 시안 화면
      comparisons/        원본과 시안의 나란한 비교 화면
      review.json         세 유형과 다섯 항목의 판정 및 근거
      approval.json       이 버전에 대한 실제 사용자 확인 증빙
    feedback.json         거부 의견과 수정·재확인 연결 기록
```

검토 버전은 소단원, 계획 버전, 대표 장표 세 개, 비교 원본, 시안의 파일 또는 Figma 노드, 실제 확인한 화면과 각각의 해시로 식별한다. Figma 노드 ID가 같아도 내용이 바뀌면 동일 버전으로 간주하지 않는다. URL 또는 파일 이름만으로 확인 대상을 식별하지 않는다.

이전 검토 버전과 사용자 응답을 덮어쓰지 않는다. 최신 버전의 판정과 이전 버전의 승인을 섞어 통과시키지 않는다. 경로를 단순히 옮겼다는 이유로 내용 해시 불일치를 무시하지 않는다.

## 2. 항목별 판정과 증거

그림 중심, 표와 수식, 비교 사진의 세 유형과 제목 계층·자료 크기·여백·이미지 배경·테두리의 다섯 항목은 기준 설계를 따른다.

판정에는 대상 장표와 버전, 항목 코드, 상태, 판단 이유, 비교 화면과 해시, 판정 주체를 기록한다. 확인하지 못한 항목은 unverified로 남긴다. 해당 요소가 없는 경우에만 not_applicable을 쓰고 이유를 남긴다.

검사 대상이 비거나 비교 화면이 없으면 실패한다. 기록이 채워졌다는 사실을 시각 품질의 자동 보증으로 설명하지 않는다. 스크립트는 누락·버전·상태·증빙의 일관성을 검사하고, 실제 디자인 적합성은 비교 화면 검토와 사용자 확인으로 판단한다.

## 3. 사용자 거부 의견의 추적

각 의견에 고유 번호를 부여한다. 의견 번호는 소단원 안에서 중복되지 않고 이력을 보존한다.

한 의견의 기록에는 다음 연결이 있어야 한다.

1. 거부 내용: 사용자 원문 또는 의미를 보존한 인용, 해당 응답의 식별 정보, 대상 버전과 장표, 전체 또는 국소 영향 범위
2. 수정본: 의견에 대응하는 새 버전, 변경 내용과 비교 증거
3. 재확인: 실제 검토 결과, 사용자 디자인 확인이 필요한 경우 해당 사용자 응답과 정확한 대상 버전

의견 상태는 open, revised, resolved로 구분한다. 수정본을 만들었다는 사실만으로 resolved가 되지 않는다. revised는 수정 후 재확인이 남았음을 뜻한다. reopened 이력은 별도 사건으로 보존하고 다시 open으로 처리한다.

전체 스타일 거부는 미해결인 동안 전체 제작·완료를 막는다. 수식 누끼처럼 특정 요소만 고친 작업은 그 국소 의견의 수정 증거가 될 수 있으나 전체 스타일 거부를 자동 해소하지 않는다. 실제 사용자 디자인 확인이 현재 대표 장표 버전에 연결되고 해당 거부 범위를 충족해야 전체 스타일 의견을 resolved로 전환한다.

새로운 국소 의견도 해결되지 않은 채 전체 완료로 처리하지 않는다. 해당 장표의 비교 검토가 필요하며, 대표 디자인 확인의 유효성에 영향을 주는 변경이면 사용자 확인 단계로 돌아간다. 사용자의 무응답, 과거 계획 승인, 에이전트가 작성한 승인 문구는 재확인 증빙이 아니다.

거부 범위가 모호하면 임의로 좁혀서 해결 처리하지 않는다. 분명한 국소 수정은 계속할 수 있으나 전체 스타일 문제가 해소된 것으로 보고하지 않는다.

## 4. 삼투 현상 복사본 선행 시험

판정기 구현 후 실제 소단원에 적용하기 전에 삼투 현상 작업 폴더의 격리된 시험용 복사본으로 검증한다. 교과서·원본 PPT·실제 Figma 파일과 실제 승인 기록은 시험을 위해 변경하지 않는다. 실패 주입은 시험용 파일과 시험용 승인 데이터에만 수행한다.

필수 시험은 다음과 같다.

| 사례 | 기대 결과 |
|---|---|
| 세 유형·다섯 항목·비교 증거·현재 버전 확인·미해결 의견 0건 | 시험 모드에서 정상 통과 |
| 대표 디자인 사용자 확인 누락 | 실패 |
| 이전 시안의 확인을 변경된 시안에 연결 | 실패 |
| 비교 화면 누락 또는 파일 해시 불일치 | 실패 |
| 대표 장표 유형 누락·중복·빈 검사 대상 | 실패 |
| failed 또는 unverified 항목 잔존 | 실패 |
| not_applicable 사유 누락 | 실패 |
| 사용자 거부 의견 open 또는 revised 잔존 | 실패 |
| 국소 수식 수정만으로 전체 스타일 거부를 해결 처리 | 실패 |
| 시험용 승인으로 실제 최종 결과물을 발행하려 함 | 실패 |
| 검토 뒤 시안이 바뀐 상태에서 재개 | 현재 확인을 무효로 판정하고 관련 단계로 복귀 |

정상 시험의 합성 승인은 시험 모드에서만 허용한다. 실제 사용자가 대표 디자인을 승인한 것으로 소급하지 않는다. 시험 결과에는 입력 조건, 기대 판정, 실제 판정과 증거를 남긴다. 테스트 개수 자체보다 각 필수 사례가 실제로 실행되어 기대대로 판정되는지를 확인한다.

현재 삼투 현상에는 전체 스타일 거부가 있었으며 이후 국소 수정만 진행되었다. 새 대표 디자인 확인 증빙이 없는 한 실제 작업을 새 게이트의 정상 통과 사례로 취급하지 않는다.

## 5. 구현·적용 경계

현재 rules.json 및 gate.py의 기존 기능과 이 확정 설계를 구분한다. 이번 문서 저장만으로 파일 구조·기계 검사·실패 복귀가 구현되었다고 보고하지 않는다.

후속 구현에서는 실제 필드와 게이트 조건을 rules.json을 기준으로 정하고 gate.py, AGENTS.md, 기존 게이트·흐름·재개 문서를 함께 정합화한다. 이전의 사용자 승인 한 곳이라는 규칙은 새 대표 디자인 확인 정책과 함께 갱신해야 한다. 판정 조건을 구현 없이 문서에서만 통과했다고 처리하지 않는다.

복사본 시험을 통과한 뒤 실제 소단원에 적용한다. 적용 시 기존 계획 승인과 보호 원본은 유지하고, 새 디자인 확인은 별도로 확보한다. 이전 최종본은 이력으로 보존하며 새 게이트를 통과한 결과물과 구분한다. 현재 결과물을 자동 삭제하거나 실제 Figma에 시험용 변경을 보내지 않는다.

기계 검사 수치와 필수 필드의 단일 기준은 구현 후 rules.json이다. 이 문서는 확정한 기록·시험 정책과 그 이유를 설명한다.
